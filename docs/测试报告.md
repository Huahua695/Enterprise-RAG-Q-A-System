## 二、背景

代码审查发现：`SECRET_KEY` 默认空串是 fail-open 的——python-jose 对空密钥不报错，
服务照常启动并签发 JWT，任何人都能伪造 admin token。本轮修复：`app/main.py`
启动时调用 `app/core/config.py` 的 `ensure_secret_key()`，未配置即拒绝启动；
离线脚本（`init_db.py` / `rebuild_index.py`）不受影响。

## 五、行为变化与影响

- **行为变化**: 缺少 `SECRET_KEY`（未创建 `.env` 或留空）时，`run.py` 启动即报
  `RuntimeError`，不再"看似正常实则可伪造 token"。README 快速开始已引导先建 `.env`。
- **不受影响**: `init_db.py`、`rebuild_index.py` 等离线脚本不调用校验函数，
  无 `.env` 时仍可执行。

## 十、任务 4：logout/token 吊销与登录限流（2026-08-31）

### 改动内容

- **token 吊销**：`create_access_token` 注入 `jti`；新增 `RevokedToken` 表
  （`create_all` 自动建表，无需手工迁移）；logout 接口把当前 token 加入黑名单
  至其原过期时间，`get_current_user` 每次请求校验黑名单；logout 时顺手清理
  已过期黑名单记录。历史 token（无 jti）跳过校验、靠自然过期，向后兼容。
- **登录限流**：新增 `app/core/rate_limit.py`（进程内滑动窗口，线程安全），
  以「用户名|IP」为键，默认 15 分钟窗口 5 次连续失败后拒绝（429），
  登录成功即清零；阈值/窗口可经 `.env` 配置。限流检查在密码验证之前执行。
- **前端**：`ProtectedRoute` 的 logout 尽力调用后端吊销接口（失败不阻塞本地登出）。

### 安全审查结论

- 限流在被 blocked 时不重复记账，窗口按失败时间滑动，冷却后自动解封
- 登录失败统一 401 文案，不引入用户名枚举新面；触发/拒绝均记日志
- 双次 logout 幂等（`db.merge`）；已知权衡：内存限流不抗 IP 轮换、
  按「用户名|IP」锁定存在针对性锁号风险，且多 worker/多实例需换 Redis（已在代码注释声明）
- 遗留：改密码后不吊销其他会话（需按用户的 token 版本号机制，后续实现）

### 测试结果

新增 `tests/test_auth_security.py` 5 用例：token 含 jti、logout 后原 token 401、
超限 429（正确密码也拒）、成功登录重置计数、窗口过期语义。全套 **22 passed**；
前端 `tsc --noEmit` 类型检查通过。

### 背景：复查发现的三项问题

## 十五、CI 流水线可用性修复：pythonVersion 对齐 + 用例环境依赖缺陷（2026-09-16）

### 背景

第十一节交付 Gitee Go 流水线时，只做了「YAML 语法解析 + 与官方示例逐字段比对」，
**没有验证过那条测试命令在 CI 条件下是否真能跑绿**（当时流水线尚未启用，无法云端执行）。

本轮改为在本地**逐条复现 CI 的执行条件**后，发现按原配置**流水线第一次运行就会失败**。

### 改动清单

| # | 文件 | 改动 | 原因 |
|---|---|---|---|
| 1 | `.workflow/master-pipeline.yml` | `pythonVersion: '3.12'` → `'3.13'` | 与本地 `backend/.venv`（Python 3.13.14）对齐，避免「本地过、CI 挂」的版本错位 |
| 2 | `.workflow/master-pipeline.yml` | `pip` / `pip3` / `python` 混用 → 统一为 `python3 -m pip` / `python3 -m pytest` | 该插件基础镜像为 CentOS，官方示例亦用 `python3`；统一用 `python3 -m` 可保证 pip 安装的包与跑 pytest 的解释器是同一个，且不依赖 `python` / `pip` 短名是否存在 |
| 3 | `backend/tests/test_embeddings_factory.py` | `test_fastembed_dispatch` 增加 `monkeypatch.setattr(settings, "EMBEDDING_PROVIDER", "fastembed")` | **本轮发现的真实缺陷**，见下 |

#### 缺陷 3 的详情

CI 命令注入了 `EMBEDDING_PROVIDER=local`（意图：CI 内不下载语义模型，保持测试封闭）。
同文件的 `test_default_provider_is_fastembed` 已按此设计写（断言 `Settings.model_fields[...].default`，
不读环境变量生效值），但 `test_fastembed_dispatch` 直接调用 `build_embeddings()` 并期望走到
fastembed 分支——**在 `EMBEDDING_PROVIDER=local` 下返回 `LocalHashEmbeddings`，断言失败**：

```text
FAILED tests/test_embeddings_factory.py::test_fastembed_dispatch
E  AssertionError: assert False
E   + where False = isinstance(<LocalHashEmbeddings object>, <class DummyEmbeddings>)
1 failed, 36 passed
```

修复方式选择「让用例显式固定 provider」，而不是「从 CI 命令里去掉该环境变量」：
后者会让 CI 的封闭性设计（不下载权重）失效，而前者同时修正了一个更本质的问题——
**单元测试不应依赖外部环境变量的取值**，被测对象的前提条件应由用例自身声明。

### 验证方法与结果

「忠实模拟 CI」的关键差异点：CI 是全新 clone，仓库内**没有 `.env`**（被 `.gitignore` 排除），
本地跑测试时该文件存在。因此模拟时用 `try/finally` 临时隐藏 `backend/.env`，并在子进程环境中
清除本机可能存在的 `EMBEDDING_PROVIDER` / `SECRET_KEY` / `LLM_API_KEY` 等变量。

| 用例 | 条件 | 结果 |
|---|---|---|
| A | `EMBEDDING_PROVIDER=local` + 无 `.env`（= 修复后的 CI 实况） | ✅ **37 passed** in 9.45s |
| B | 不注入 `EMBEDDING_PROVIDER`（走出厂默认 fastembed）+ 无 `.env` | ✅ **37 passed** in 10.08s |
| C | 本地常规环境（有 `.env`，不注入任何变量） | ✅ **37 passed** in 9.96s |
| A′ | 同 A，但**改动前**的用例代码 | ❌ 1 failed, 36 passed（复现 CI 失败） |

补充验证：

- `pyyaml` 解析 `.workflow/master-pipeline.yml` 成功，`name` / `triggers.push.branches` /
  `step` / `pythonVersion` / `commands` 逐项断言通过；
- 模拟前后校验 `backend/.env` 完整还原（`SECRET_KEY` 55 字符、两条 `LLM_API_KEY` 等均在，
  临时备份文件已消失）。

### 说明与风险

- 流水线仍未真正在云端跑过一次——本报告验证的是「命令在等价环境下能跑绿」，
  不等价于平台侧一定成功。差异项主要是依赖安装（网络、wheel 可用性）与平台镜像提供的版本。
- `pythonVersion: '3.13'`：Gitee Go 帮助中心该插件页面仍写着「支持 2.7、3.6~3.9 五个版本」，
  但其近期版本扩容公告称 Python 已覆盖 2.7~3.14，两者不一致，以**平台可视化编辑器里的下拉列表为准**。
  若报「版本不支持」，把该字段改成下拉列表中可选的版本即可（代码要求 Python 3.10+）。
- 首次运行因需安装 `fastembed`（含 `onnxruntime`）等依赖，耗时会长于本地；
  Gitee Go 免费额度为单仓库 200 分钟（永久）+ 个人每月 500 分钟，常规使用足够。
- 本流水线只跑 `backend/` 下的 37 个单元用例，**不跑** `e2e/`（那 3 个 Playwright 用例需要真实前后端），
  这是刻意设计。
