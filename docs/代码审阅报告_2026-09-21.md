## 二、Top 5 必须优先修复

| # | 问题 | 位置 | 工作量 |
|---|------|------|--------|
| 1 | 多轮对话历史完全没进 prompt，追问类问题必挂 | `app/routes/chat.py:send_question` + `app/services/rag_service.py:astream_answer` | 数小时 |

| 3 | 检索层三缺陷：无相似度分数、多库合并无全局排序、索引每次从磁盘重载 | `app/services/rag_service.py:retrieve` / `_load_vectorstore` / `_save_index` | 1–2 天 |
| 4 | 文档解析实用缺陷：GBK 文本必炸、xls 必炸、扫描 PDF 静默"成功" | `app/services/document_parser.py:parse_txt` / `parse_excel` / `parse_pdf` | 1 天 |
| 5 | 前端吞掉 SSE error 事件，LLM 配错时用户零反馈 | `frontend/src/services/chatService.ts:sendQuestion` | <1 小时 |

### Top 1：多轮对话历史未传入 LLM

- **问题**：`chat.py:send_question` 生成时只调用 `rag_engine.astream_answer(request.message, docs)`（rag_service.py:230），`Message` 表里明明存了完整历史（chat.py:85-88 还专门按 `created_at` 排序查询），但从未拼进 prompt。
- **影响**：用户问"那它的价格呢？"这类指代性追问时，模型完全不知道上一轮在聊什么，只能瞎答或答非所问。这是知识库问答最常见使用模式，演示时极易翻车。
- **改进方案**：`send_question` 里查询该 session 最近 N 条（建议 6–10 条）历史，构造 messages 传入 `astream_answer`；prompt 结构改为「历史对话（可截断） + 检索到的知识块 + 当前问题」，历史部分用 `MessagesPlaceholder` 或手动拼接均可。注意历史也要做长度截断（如每条 500 字符），防止长会话 token 爆炸。
- **优先级**：高。

### Top 2：引用溯源缺 metadata

- **问题**：`document_processor.py:process_document` 第 28 行 `rag_engine.add_documents(chunks, collection_name=f"kb_{kb_id}")` 只传了 `texts`，没传 `metadatas`；`rag_service.py:add_documents`（175 行）内部走 `FAISS.from_texts(texts, self.embeddings)`，metadatas 默认为空 dict。
- **影响**：所有 chunk 的 `Document.metadata = {}`，`chat.py:send_question` 返回的 references 里 metadata 是空对象——用户看到的引用只有一段文本片段，**不知道来自哪个文件、哪个知识库**。"企业级知识库"的引用溯源等于不存在。`init_db.py:90` 与 `rebuild_index.py:36` 同样没传，三处一致缺失。
- **改进方案**：`process_document` 构造 `metadatas=[{"source": doc.filename, "doc_id": doc_id, "kb_id": kb_id} for _ in chunks]` 传入；`add_documents` 增加 `metadatas: List[dict] | None` 参数透传给 `from_texts/add_texts`；`init_db.py` 与 `rebuild_index.py` 同步修改。改完执行 `rebuild_index.py` 重建。前端 `ChatPage.tsx` 引用卡片即可展示来源文件名。
- **优先级**：高。

### Top 3：检索层三缺陷（质量 + 性能）

- **问题 a（无分数）**：`rag_service.py:retrieve`（216 行）用 `vectorstore.similarity_search(question, k=k)`，丢弃了相似度分数。
- **问题 b（无全局排序）**：多知识库检索后直接按「库的顺序」append（209–226 行），`merged[: min(k*3, 15)]` 只是截断。第一个库的第 5 条可能比第三个库的第 1 条分数低得多，却排前面进 prompt。
- **问题 c（无缓存 + 非原子写）**：每次 `retrieve` 都调 `_load_vectorstore` → `_read_index`，`faiss.deserialize_index` + `pickle.load` 全量读盘；会话未绑定知识库时回退「检索全部可见知识库」（chat.py:129-132），N 个库 = N 次磁盘反序列化。同时 `_save_index`（106–118 行）先写 `index.faiss` 再写 `index.pkl`，两步非原子，`retrieve` 不持锁，后台向量化写入与前台检索并发时存在读到「新 faiss + 旧 pkl」的撕裂窗口。
- **影响**：检索质量不保（无关内容也进 prompt，浪费 token 且诱导幻觉）；问答延迟随知识库数量线性放大；并发场景偶发检索异常（虽有 try 兜底但结果错误）。
- **改进方案**：
  1. 改用 `similarity_search_with_score`，收集 `(doc, score, kb_name)`，跨库**按分数全局降序排序**后取 top-k；
  2. 加相似度阈值（如内积 < 0.3 的结果丢弃），过滤后不足时明确返回"知识库中没有找到相关信息"；
  3. `RAGEngine` 内加 `self._store_cache: dict[str, FAISS]`，`_load_vectorstore` 命中缓存直接返回，`add_documents`/`delete_collection` 时失效对应 key（注意加锁）；
  4. `_save_index` 改为先写同目录临时文件再 `os.replace` 原子替换两个文件（或整个目录写临时目录后 rename）。
- **优先级**：高。

### Top 4：文档解析实用缺陷（中文场景必踩）

- **问题 a**：`document_parser.py:parse_txt`（46–48 行）硬编码 `encoding="utf-8"`，Windows 记事本另存的 GBK 中文 txt 直接 `UnicodeDecodeError`。
- **问题 b**：白名单 `ALLOWED_UPLOAD_TYPES`（config.py:45）允许 `xls`，但 `parse_excel` 走 `pd.read_excel`，pandas 2.x 读 .xls 需要 `xlrd`，requirements.txt 里没有——xls 上传必在后台解析时报错（用户看到的是文档状态 failed）。
- **问题 c**：`parse_pdf` 对扫描版（图片型）PDF 返回空字符串，`split_document` 得到 0 个块，`add_documents([])` 直接 return（rag_service.py:176-177），文档状态照常置 `completed`、`chunk_count=0`——**静默成功但内容为空**，用户毫无感知。
- **问题 d**：`parse_word`（18–25 行）只遍历 `doc.paragraphs`，不遍历 `doc.tables`——Word 里画的表格数据全部丢失。
- **改进方案**：a) txt 用 `charset-normalizer`（fastembed 已带）或 try 链 `utf-8 → gbk → gb18030` 检测编码；b) 要么把 `xls` 移出白名单，要么加 `xlrd>=2.0.1` 依赖；c) `parse_pdf` 检测提取文本长度 < 阈值（如 50 字符/千页）时抛"疑似扫描件，暂不支持 OCR"；`process_document` 里 `chunks` 为空时置 failed 并写明原因；d) `parse_word` 补 `for table in doc.tables` 遍历 `table.rows` 拼 CSV 行。
- **优先级**：高。

### Top 5：前端吞掉 SSE error 事件

- **问题**：`chatService.ts:sendQuestion`（64–74 行）的 SSE 解析只处理 `data.type === 'answer'` 和 `'references'`，后端明确发送的 `{"type": "error", "message": ...}`（chat.py:161/165，含"LLM 未配置"的具体指引）落到 `catch {}` 里被静默吞掉。
- **影响**：LLM 配置错误、服务内部错误时，前端表现是"流式输出静默结束"，无任何提示。用户（和答辩评委）无从排查。
- **改进方案**：`sendQuestion` 增加 `onError?: (msg: string) => void` 回调，解析到 `type === 'error'` 时调用；`ChatPage.tsx` 在消息流里渲染错误气泡（后端 message 已是友好中文文案，可直接展示）。
- **优先级**：高（但修复成本极低）。
