## 二、背景

代码审查发现：`SECRET_KEY` 默认空串是 fail-open 的——python-jose 对空密钥不报错，
服务照常启动并签发 JWT，任何人都能伪造 admin token。本轮修复：`app/main.py`
启动时调用 `app/core/config.py` 的 `ensure_secret_key()`，未配置即拒绝启动；
离线脚本（`init_db.py` / `rebuild_index.py`）不受影响。

## 五、行为变化与影响

- **行为变化**: 缺少 `SECRET_KEY`（未创建 `.env` 或留空）时，`run.py` 启动即报
  `RuntimeError`，不再"看似正常实则可伪造 token"。README 快速开始已引导先建 `.env`。
- **不受影响**: `init_db.py`、`rebuild_index.py` 等离线脚本不调用校验函数，
  无 `.env` 时仍可执行。

## 十、任务 4：logout/token 吊销与登录限流（2026-08-31）

### 改动内容

- **token 吊销**：`create_access_token` 注入 `jti`；新增 `RevokedToken` 表
  （`create_all` 自动建表，无需手工迁移）；logout 接口把当前 token 加入黑名单
  至其原过期时间，`get_current_user` 每次请求校验黑名单；logout 时顺手清理
  已过期黑名单记录。历史 token（无 jti）跳过校验、靠自然过期，向后兼容。
- **登录限流**：新增 `app/core/rate_limit.py`（进程内滑动窗口，线程安全），
  以「用户名|IP」为键，默认 15 分钟窗口 5 次连续失败后拒绝（429），
  登录成功即清零；阈值/窗口可经 `.env` 配置。限流检查在密码验证之前执行。
- **前端**：`ProtectedRoute` 的 logout 尽力调用后端吊销接口（失败不阻塞本地登出）。

### 安全审查结论

- 限流在被 blocked 时不重复记账，窗口按失败时间滑动，冷却后自动解封
- 登录失败统一 401 文案，不引入用户名枚举新面；触发/拒绝均记日志
- 双次 logout 幂等（`db.merge`）；已知权衡：内存限流不抗 IP 轮换、
  按「用户名|IP」锁定存在针对性锁号风险，且多 worker/多实例需换 Redis（已在代码注释声明）
- 遗留：改密码后不吊销其他会话（需按用户的 token 版本号机制，后续实现）

### 测试结果

新增 `tests/test_auth_security.py` 5 用例：token 含 jti、logout 后原 token 401、
超限 429（正确密码也拒）、成功登录重置计数、窗口过期语义。全套 **22 passed**；
前端 `tsc --noEmit` 类型检查通过。

### 评测结果（12 用例，k=5，索引建在临时目录）

| provider | Recall@5 | MRR@5 | 第 1 名命中数 |
|---|---|---|---|
